# Мониторинг серверов

Как LobbyHub опрашивает игровые серверы, что из них получает и куда это складывает.

Актуально на 27.07.2026. Реализованы все три протокола: Minecraft, Source (Rust) и FiveM.

---

## 1. Общая картина

```
cron (раз в минуту)
  └─ servers:query .................. диспетчер: кого пора спросить
       ├─ отбор: next_query_at <= now, is_active, лимит batch_size
       ├─ отсев игр без драйвера
       ├─ HostSpread ................. перемешать по хостам + лимит на хостера
       └─ в очередь `monitoring`: QueryServer на каждый сервер
            └─ воркер очереди
                 ├─ ServerQueryManager → драйвер по протоколу игры
                 │    ├─ MinecraftQueryDriver ... TCP, Server List Ping
                 │    ├─ SourceQueryDriver ...... UDP, A2S_INFO + challenge
                 │    └─ FiveMQueryDriver ....... HTTP, /dynamic.json
                 ├─ успех  → снапшот в `servers` + точка в `server_stats`
                 └─ провал → офлайн-точка + удвоение паузы (бэкофф)

cron (раз в час)
  └─ stats:rollup ................... сырые точки → дневные итоги, аптайм, прунинг
```

Ключевой принцип разделения: **драйвер знает только протокол, задача знает только базу.** Драйвер не обращается к БД и никогда не сообщает «сервер офлайн» — он либо возвращает данные, либо бросает `QueryFailed`. Решение, что считать простоем, принимает задача.

## 3. Цикл опроса

### 3.1. Отбор (диспетчер)

Раз в минуту. Берёт активные серверы, у которых `next_query_at <= now()`, сортируя по этому же полю (самые просроченные первыми), не больше `batch_size` (500) за раз.

Серверы игр без драйвера отбрасываются с предупреждением — иначе они падали бы каждую минуту.

Диспетчер **сам не опрашивает**: опрос сервера на другом континенте занимает до 5 секунд, и последовательно 500 серверов растянулись бы на полчаса. Он только ставит задачи в очередь `monitoring`, где их разбирают воркеры параллельно.

### 3.2. Вежливость к хостерам

У провайдера за одним IP могут стоять сотни серверов, а сортировка по сроку опроса ставит их в батч подряд — со стороны это выглядит как сканирование портов.

`HostSpread` группирует батч по `ip_address` (или по `host`, если IP ещё не резолвился) и раскладывает round-robin: `a1, b1, c1, a2, b2, a3`. Плюс лимит `max_per_host` (10) на батч — излишек не выбрасывается, а остаётся просроченным и уходит в следующий проход, о чём диспетчер сообщает.

### 3.3. Опрос (задача)

`QueryServer` — одна попытка (`$tries = 1`). Повторы бессмысленны: недоступность это не сбой задачи, а результат измерения, и его надо записать. Повторную попытку планирует бэкофф.

### 3.4. Запись

**Успех** → `servers`: `status=online`, игроки, карта, версия, MOTD, IP, страна, `last_queried_at`, `last_online_at`, `failed_queries_count=0`, `next_query_at` по уровню.
**Провал** → `servers`: `status=offline`, `players_online=0`, счётчик провалов +1, `next_query_at` по бэкоффу.

В оба случая — строка в `server_stats`. Пишется через `upsert` по `(server_id, recorded_at)`: две задачи в одну секунду не должны конфликтовать по первичному ключу.

## 4. Протоколы

### 4.1. Minecraft — Server List Ping (Java, 1.7+)

TCP на `25565` по умолчанию. Пакет = `VarInt(длина) + VarInt(id) + тело`; строки — `VarInt(длина) + UTF-8`.

```
→ Handshake:      id 0x00 | protocol_version | host | port (uint16 BE) | next_state=1
→ Status request: id 0x00 (пустой)
← Status:         id 0x00 | JSON
```

**SRV-резолв.** Если порт равен дефолтному для игры и хост не IP — читаем `_minecraft._tcp.<домен>`, как ванильный клиент. Без этого серверы на доменах с нестандартным портом недоступны.

Из JSON берём `players.online`, `players.max`, `version.name`, `description`. Скрытый онлайн приходит как `-1` и зажимается в 0.

**MOTD** бывает строкой или деревом компонентов (`{"text":…,"extra":[…]}`). Дерево склеивается рекурсивно, `§`-коды цвета вырезаются, пробелы нормализуются **один раз на собранной строке** — если тримить каждый вложенный компонент, пробелы между частями съедаются (`Hypixel Network[1.8-1.21]` вместо `Hypixel Network [1.8-1.21]`).

Легаси-пинг `0xFE` (до 1.7) не поддержан.

### 4.2. Source / A2S — Rust, ARK, CS2, GMod, 7 Days to Die

UDP на `28015` для Rust. Протокол **стандартный Valve**, никакой раст-специфики в транспорте нет — тот же драйвер работает для всей семьи.

**Обмен всегда двухшаговый:**

```
→ FF FF FF FF 'T' "Source Engine Query\0"
← FF FF FF FF 'A' <4 байта challenge>        ← не данные, а пропуск
→ FF FF FF FF 'T' "Source Engine Query\0" <challenge>
← FF FF FF FF 'I' <данные>
```

С конца 2020 года первый запрос никогда не возвращает данные — сервер отдаёт челлендж, который надо вернуть дословно. Некоторые челленджат дважды, отсюда `source.challenge_retries`.

**Порядок полей** фиксированный, без имён и разделителей — читать можно только подряд с начала:

```
protocol | name | map | folder | game | appid(uint16)
players(1B) | max_players(1B) | bots | server_type | environment | visibility | vac
[+3 байта, если appid = 2400 (The Ship)]
version
[EDF: флаг-байт, далее по флагам]
  0x80 игровой порт (uint16)   0x10 steam id (8B)
  0x40 порт+имя SourceTV       0x20 строка тегов        0x01 game id
```

Всё, что нам не нужно (боты, ОС, VAC, Steam ID), всё равно читается — иначе не доехать курсором до нужных полей.

**Счётчикам игроков в байтовых полях верить нельзя.** На них отведён один байт, то есть максимум 255 — сервер на 300 слотов физически не может себя описать. Rust дублирует настоящие числа в строке тегов, и мы предпочитаем их:

```
mp205, cp202, qp0, born1784811433, gmrust, EU, v2631, rustmaps, ...
     ↑        ↑     ↑         ↑
   мест   игроков  очередь   unix-время последнего вайпа
```

Замер на живом сервере: байтовое поле показало **225** игроков, тег `cp` — **202**. Байт врал. Ту же логику использует BattleMetrics. Регулярки узкие (`^cp\d+$`, `^mp\d+$`), на теги других игр не срабатывают, поэтому драйвер остаётся общим.

**Название сервера пишется в `motd`, не в `name`.** У A2S нет MOTD, его живой аналог — заголовок сервера; перезаписывать им `name` из каталога нельзя, это поле выбирает владелец.

**A2S_PLAYER для Rust бесполезен.** Список игроков приходит (237 записей), но имена подменены синтетическими, счёт у всех 0, длительности слипаются. Facepunch защищается от скрейпинга. Фича «профили игроков» в стиле GameTracker для Rust недостижима.

Разбитые на несколько датаграмм ответы (`FF FF FF FE`) отвергаются: для A2S_INFO они не встречаются.

### 4.3. FiveM / CitizenFX

Обычный HTTP на порту `30120`, никакого бинарного протокола. Сервер отдаёт три эндпоинта:

| Эндпоинт | Что внутри |
|---|---|
`/dynamic.json` | `clients`, `sv_maxclients`, `hostname`, `mapname`, `gametype` |
`/info.json` | номер сборки, ресурсы, переменные `sv_*` |
`/players.json` | полный список игроков |

Запрашиваем **только `dynamic.json`**: в нём есть всё, что показывает каталог, а один запрос на опрос удерживает FiveM в той же цене, что и остальные игры. Модель нагрузки считается в воркеро-секундах, и каждый лишний эндпоинт — ещё одна.

Из-за этого `reported_version` у FiveM пустой: номер сборки лежит в `info.json`. Если версия понадобится в карточке, это осознанный размен на второй запрос.

**Названия серверов забиты цветовыми кодами** `^1`..`^9` и тегами вида `~r~`, иначе они попали бы в каталог буквальным текстом:

```
^2[EU] ^7Los Santos ^1Roleplay ^7| ~b~whitelist~s~   →   [EU] Los Santos Roleplay | whitelist
```

Как и у Rust, заголовок сервера пишется в `motd`, а не в `name`.

**Ответ проверяется на принадлежность FiveM.** Если в теле нет `clients` и `sv_maxclients`/`maxclients` — это не FiveM-эндпоинт, а посторонний веб-сервер на том же порту, и записывать его как живой пустой сервер нельзя. Такой ответ считается битым.

Отдельно обрабатывается `403`: это включённый `sv_endpointPrivacy`, то есть сервер жив, но закрыл статистику. Для нас неотличимо от недоступности.

## 5. Что получаем и куда кладём

`QueryResult` — единый DTO для всех игр, 10 полей:

| Поле DTO | Minecraft | Source / Rust | FiveM | Куда пишется |
|---|---|---|---|---|
`playersOnline` | `players.online` | тег `cp`, иначе байт | `clients` | `servers.players_online`, `server_stats.players_online` |
`playersMax` | `players.max` | тег `mp`, иначе байт | `sv_maxclients` | `servers.players_max`, `server_stats.players_max` |
`version` | `version.name` | поле `version` | — | `servers.reported_version` |
`map` | — | поле `map` | `mapname` | `servers.map` |
`motd` | `description` | поле `name` | `hostname` | `servers.motd` |
`latencyMs` | RTT обмена | RTT **последнего** обмена | RTT запроса | `server_stats.latency_ms` |
`ipAddress` | резолв хоста | резолв хоста | резолв хоста | `servers.ip_address` → страна |
`gamePort` | — | EDF, флаг `0x80` | — | `servers.game_port` |
`wipedAt` | — | тег `born` | — | `servers.wiped_at` |
`playersQueued` | — | тег `qp` | — | `servers.players_queued` |

Дополнительно задача пишет: `status`, `last_queried_at`, `last_online_at`, `failed_queries_count`, `next_query_at`, `country_id`.

**Пустое не перезаписывает заполненное.** Поля, которых протокол не умеет сообщать, приходят как `null`, и задача такие колонки не трогает — иначе опрос майнкрафт-сервера обнулял бы ему карту, а опрос Rust затирал бы MOTD.

Задержка считается по **последнему** обмену, а не по всему опросу: у A2S их два (челлендж и данные), у Minecraft один, и без этого Rust выглядел бы вдвое медленнее при одинаковой сети. Теперь число значит одно и то же во всех играх — один сетевой round-trip.

**Страна** определяется один раз — только если `country_id` пуст. IP сервера почти не меняется, а держать читалку GeoLite2 на горячем пути всего каталога незачем.

### История

`server_stats` — по строке на опрос: `(server_id, recorded_at)`, `is_online`, игроки, слоты, задержка. Живёт 14 дней.
`server_daily_stats` — дневные итоги: средний/минимальный/пиковый онлайн, число точек, аптайм. Живёт вечно.

Прунинг сырых точек **не разрушает историю** — дневные итоги остаются. Подробнее — в `stats:rollup`.

## 6. Каденция

### Уровни (живой сервер)

Выбираются по онлайну, измеренному **только что**, сверху вниз, первое совпадение:

| Онлайн | Интервал |
|---|---|
100+ | 120 с |
10+ | 300 с |
1+ | 900 с |
0 | 3600 с |
продвигаемый (`promoted_until` в будущем) | 120 с при любом онлайне |

Разброс горячий/пустой — **30 раз**. Это главный рычаг нагрузки: основная масса любого каталога пустая, и опрашивать её как топовый сервер — чистая потеря. Платящий клиент держится в горячем уровне независимо от онлайна.

### Бэкофф (сервер не ответил)

`interval × 2^провалов`, но не больше `max_interval`: 600 с → 1200 с → 2400 с → … → 6 часов.

Бэкофф намеренно считается от **базового** `interval`, а не от уровня: упавший сервер отдаёт ноль игроков, и по уровням любая авария сразу улетала бы в ленивый час вместо быстрых первых повторов.

Мёртвые серверы перестают занимать очередь, но из каталога не исчезают: ожил — счётчик сбросился, ритм вернулся.

## 8. Команды

```bash
# Опрос по расписанию (то, что делает cron)
php artisan servers:query

# Один сервер, игнорируя расписание, без очереди — для отладки

# Ограничить батч
php artisan servers:query --limit=50

# Пересобрать конкретный день
php artisan stats:rollup --date=2026-07-20 --prune-days=0
```

## 9. Эксплуатация

### Что должно быть запущено

Два процесса. Без первого расписание не срабатывает, без второго задачи копятся в очереди и опрос не идёт.

```bash
php artisan schedule:work                 # планировщик, запускает задачи по расписанию
php artisan queue:work --queue=monitoring --tries=1 --max-time=3600
```

`schedule:work` — долгоживущий процесс вместо строки в crontab: одинаково работает на любой машине и держит всю конфигурацию в одном месте.

`--tries=1` намеренно: недоступность сервера — это законный результат, который джоб уже записал как простой. Повтор только исказил бы историю. `--max-time=3600` перезапускает воркер раз в час, чтобы утечка не накапливалась.

**На macOS** готовые сервисы лежат в `deploy/launchd/`. Они переживают перезагрузку:

```bash
cp deploy/launchd/*.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/gg.lobbyhub.scheduler.plist
launchctl load ~/Library/LaunchAgents/gg.lobbyhub.worker.plist
```

Логи — в `storage/logs/scheduler.log` и `storage/logs/worker.log`.

Расписание прописано в `routes/console.php`:

| Команда | Как часто |
|---|---|
`servers:query` | каждую минуту |
`counters:refresh` | каждые 5 минут |
`ranking:recompute` | каждые 15 минут |
`stats:rollup --days=2` | ежечасно |

Все с `withoutOverlapping()`. Обнаружения серверов в расписании **нет** намеренно: `discovery:steam` за один проход может добавить тысячи серверов, и это решение об объёме, а не фоновая рутина.

### GeoLite2

Определение страны молча не работает, пока нет файла базы — мониторинг при этом не ломается, серверы остаются без страны.

1. Бесплатный ключ на maxmind.com → Download Databases → **GeoLite2 Country**, формат `.mmdb` (не CSV).
2. Положить в `storage/app/geoip/GeoLite2-Country.mmdb` либо указать путь в `GEOLITE2_COUNTRY_DB`.

Включится само. MaxMind обновляет базу еженедельно — со временем стоит поставить `geoipupdate` по крону.

### За чем следить

Отставание — единственный сбой, который иначе проходит молча: каденция незаметно уползает с 2 минут на 20, графики редеют, аптайм теряет точность, ошибок в логах нет.

Два механизма: диспетчер сам пишет предупреждение в вывод и в лог, когда просроченных больше, чем влезает в батч; `monitoring:status` показывает отношение фактических опросов за час к ожидаемым по уровням. Ниже 90% — разбираться.

## 10. Замеры и нагрузка

Реальное время одного опроса:

| Исход | Время |
|---|---|
Rust ответил | 244 мс (два round-trip) |
Minecraft ответил | 560 мс |
Порт закрыт (ICMP unreachable) | **2 мс** |
Порт фильтруется, тишина | **5008 мс** (полный таймаут) |

Дефицитный ресурс — не процессор и не трафик (~200 байт на обмен), а **воркеро-секунды ожидания**. Молчащий сервер дороже живого в 2500 раз, и именно от этого спасает бэкофф: в устойчивом режиме живой сервер стоит ~115 воркеро-секунд в сутки, молчащий на 6-часовом интервале — ~20.

Оценка при 40% живых серверов:

| Серверов | Воркеров | Записей в БД/с | Сырых точек | Диск (14 дней) |
|---|---|---|---|---|
2 500 | 1–2 | ~17 | 720 тыс./сутки | ~1 ГБ |
10 000 | 8–10 | ~65 | 2,9 млн/сутки | ~4 ГБ |
100 000 | ~60 | ~660 | 28,8 млн/сутки | ~36 ГБ |

**Потолок текущего конфига ≈ 2500 серверов**: 500 за минуту — это 720 тыс. опросов в сутки, а серверу при 5-минутной каденции нужно 288 в сутки. Уровни каденции отодвигают потолок в 5–10 раз, потому что пустые серверы опрашиваются раз в час.

Порядок расширения по мере роста: поднять `batch_size` и число воркеров → очередь с базы на Redis (таблица `jobs` становится узким местом) → партиционирование `server_stats` по дате с `DROP PARTITION` вместо `DELETE` → Steam Web API для массового обновления вместо поштучного опроса.

## 12. Порты: три разных числа

Их легко перепутать, а последствия разные.

| Поле | Что это | Кто заполняет |
|---|---|---|
`port` | Порт, введённый при добавлении. Входит в уникальный ключ `(game_id, host, port)`, то есть это **идентичность записи** | Владелец, один раз |
`query_port` | Куда мониторинг посылает пакеты, если отличается от `port` | Владелец или админ |
`game_port` | Порт подключения, как его сообщил **сам сервер** | Мониторинг, на каждом опросе |

`Server::queryPort()` = `query_port ?? port`. Дефолт игры в этой цепочке намеренно **не участвует**: сервер на нестандартном порту опрашивался бы по дефолту игры и стабильно висел бы офлайном. `games.default_query_port` остался подсказкой для формы добавления.

`Server::address()` = `host:(game_port ?? port)` — игроку показывается то, что сообщил сервер, с откатом на введённое владельцем. Проверено на живом сервере: опрос идёт на 28015, в карточке `eu-main.rusticated.com:28010`.

`port` не перезаписывается никогда: это сломало бы идентичность записи на каждом опросе и могло упасть по уникальному индексу, а введённое владельцем значение подменялось бы данными, которые сервер может сообщить неверно.

## 13. Кеш челленджа A2S

Замер на живом сервере показал, что челлендж переиспользуем: он принимается повторно, **с другого сокета** (то есть с другого исходного порта) и как минимум через 30 секунд. Поэтому он кешируется по адресу на час (`source.challenge_ttl`), и обычный опрос Rust укладывается в один обмен вместо двух.

Устаревший челлендж не стоит ничего: сервер ответит `A` с новым, существующий цикл повторит запрос и обновит кеш. Хуже прежнего поведения не станет никогда.

Две детали, на которых это уже один раз сломалось:

- Челлендж — **сырые 4 байта**, и текстовые кеш-хранилища (database, Redis) отвергают невалидный UTF-8. Хранится hex-строкой. Первый же тестовый запуск случайно получил печатный ASCII и прошёл, а следующий уронил всю команду — ровно та ошибка, которая в бою ломается через раз.
- Ошибки кеша **проглатываются**: кеш это оптимизация, и он не имеет права утаскивать мониторинг за собой. Максимум, что теряется — один лишний обмен.

Эффект на живом сервере: задержка Rust упала с 244 мс до 97–104 мс. Тут сложились две правки — замер только последнего обмена и сэкономленный round-trip.

## 14. Добавление сервера из формы

`POST /api/games/{game}/servers` — второй, помимо discovery, вход в каталог. Форма спрашивает ровно одно: адрес, к которому подключается игрок. Второе поле (query-порт) заполняется, только если он отличается от игрового — см. раздел 12.

Порядок проверок в `ServerSubmission` выбран так, чтобы каждая следующая была дороже предыдущей:

1. **Разбор адреса** (`ServerAddress`). Принимаем то, что реально вставляют: `connect 1.2.3.4:28015`, `steam://connect/…`, `http://host:30120/`, голый домен (тогда порт — дефолт игры), IPv6 в скобках. Одноуровневые имена вроде `localhost` отсекаются: это никогда не адрес, к которому подключится кто-то ещё.
2. **Дубликат** — до DNS и до сети. Ищем по `(game_id, port)` и совпадению `host` **или** `ip_address`: одну и ту же машину добавляют то доменом, то IP, и уникальный индекс это не ловит. Ответ 409 с ссылкой на существующий листинг, а не отказ.
3. **Публичность IP.** Домен резолвится, приватные и зарезервированные диапазоны отклоняются. Это не косметика: FiveM-драйвер ходит HTTP-запросом, и без этой проверки форма превращается в SSRF-зонд по внутренней сети.
4. **Опрос.** Собирается **несохранённая** `Server` с игрой в отношении и отдаётся обычному драйверу. Не ответил — 422 с текстом про query-порт, в базе не остаётся ничего.

**Сервер попадает в листинг сразу, в том же запросе.** К моменту записи он уже опрошен — в этом и смысл проверки на шаге 4, — поэтому измерение записывается тут же, и форма возвращает `status: online` с настоящим онлайном. Ждать больше нечего.

Раньше здесь писался кандидат со статусом `unknown`, а публиковал его `QueryServer` из очереди. Это было неверно дважды: измерение, ради которого мы стучались к серверу, выбрасывалось, а публикация зависела от того, поднят ли воркер — если нет, сервер владельца не появлялся вообще, и на странице ничто не объясняло почему.

Запись при этом по-прежнему идёт через `QueryServer`, которому передаётся уже полученный `QueryResult` (`dispatchSync($server, $result)`). Одна реализация «записать измерение» — статус, каденция, точка истории, гео, догрузка деталей, — а не вторая копия в форме, которая разъедется с первой. Платим тем, что запрос заодно пишет точку истории и тянет детали сервера, — но и то и другое нужно странице, на которую отправитель сейчас попадёт.

Ранее удалённый сервер восстанавливается на месте: slug — публичный URL, а история стоит дороже новой записи.

### 14.1. Три исхода, а не два

Форма различает `created`, `listed` и `error`. «Уже в каталоге» — **не ошибка**: адрес верен, сервер настоящий, и то, чего человек хотел, уже так. Раньше это шло по одной ветке с настоящими отказами и подсвечивалось красным, то есть форма ругалась на того, чья единственная вина — что он не знал, что сервер у нас есть.

Теперь это нейтральный тост (`toast.info`, поверхность вместо заливки) с кнопкой «Go to server». Поле адреса при этом не помечается невалидным — с ним всё в порядке.

Поля очищаются в обоих неотказных случаях: и когда сервер только что добавлен, и когда он уже был. В обоих адрес в поле отработал, и оставлять его — приглашать повторить то, что уже произошло. При отказе адрес остаётся: его нужно поправить, а не набирать заново.

### 14.2. Почему отказ — это четыре разных отказа

`QueryFailed` несёт причину значением (`App\Enums\QueryFailure`), а не только в тексте: мониторингу она безразлична — недоступность есть недоступность, — но форма разговаривает с человеком, который пытается опубликовать свой сервер, и «порт закрыт» и «порт открыт, но никто не ответил» отправляют его в противоположные концы конфигурации.

| Причина | Что говорим |
| --- | --- |
| `Unresolvable` | домен не резолвится — проверьте имя или впишите IP |
| `Unreachable` | на адресе никто не слушает — сервер запущен? порт открыт наружу? |
| `Silent` | **соединение приняли, ответа нет** |
| `Malformed` | ответили, но нечитаемо — возможно, адрес ведёт на прокси или панель |

`Silent` — тот случай, ради которого это разведено. Раньше на любой отказ выдавалась одна фраза «проверьте query-порт», и в этом случае она врала: порт демонстративно открыт, он только что принял TCP-соединение. Теперь текст указывает на настоящих подозреваемых — выключенный status на сервере и фильтрацию на стороне хостинга.

Формулировка зависит от протокола (`QueryProtocol::isConnectionOriented()`). У TCP и HTTP есть рукопожатие, поэтому «приняли и промолчали» — это факт. У A2S его нет: UDP-тишина одинаково покрывает закрытый порт, фаервол и проигнорировавший нас сервер, и там текст остаётся общим. Утверждать «порт открыт» мы в этом случае не вправе.

Лимит `submissions` — 10 в час на IP (`AppServiceProvider`). Каждая отправка заставляет нас постучаться по чужому адресу, и это единственный публичный эндпоинт с такой особенностью.

Фронт: `/add-server` — выбор игры, `/games/{game}/add-server` — сама форма. Требования в блоке «Before you add it» собираются из `games.query_protocol`, поэтому для Minecraft там `enable-status`, для Source — открытый UDP, для FiveM — `sv_endpointPrivacy`.

## 15. Список серверов игры

`/games/{game}` — и те же самые маршруты фасетов под ним: `/games/{game}/{mode}`, `/version/{v}`, `/country/{c}`. Один компонент (`GameListing`) на все, чтобы страница фасета не оказалась урезанной копией главной.

### 15.1. Два слоя

Первая страница выдачи запрашивается **на сервере**, внутри кешированной оболочки, и уезжает в HTML. Это не оптимизация, а условие индексации: список серверов — единственное, ради чего страницу открывает и человек, и краулер.

Всё, что происходит дальше — чипы, поиск, «Load more» — идёт в API напрямую из браузера. Полная навигация ради смены одного фильтра перерисовывала бы оболочку, которая не изменилась.

Состояние фильтров зеркалится в query-строку через `history.replaceState`, а не `router.push`: страница пререндерена и закеширована, и push просил бы Next заново разрешить маршрут, который остался прежним. Плата — при заходе по чужой ссылке (`?status=offline&view=grid`) нужен один дополнительный запрос уже после гидратации; состояние применяется **вместе** с приехавшими строками, иначе чипы успели бы соврать про список, которого ещё нет.

Альтернатива — читать `searchParams` на сервере — сделала бы весь маршрут динамическим и выбросила пререндер, на котором каталог держится.

### 15.2. Догрузка при прокрутке

Следующая страница запрашивается, когда конец списка попадает в поле зрения: `IntersectionObserver` следит за меткой перед кнопкой, с запасом в 700px, поэтому строки обычно уже на месте к моменту, когда дочитан последний видимый ряд.

Кнопка при этом остаётся. Она нужна тем, кто идёт с клавиатуры, и она же — то, во что вырождается страница в браузере без `IntersectionObserver`.

**Бесконечной прокрутки нет, и это осознанно.** Строки не виртуализованы, у крупной игры их тысячи, а колонка «Recent votes» ниже 2xl стоит **после** списка — вместе с подвалом. Список, который отрастает каждый раз, когда к его концу подходишь, убирает всё это из досягаемости навсегда. Поэтому прокрутка приносит пять страниц (`AUTO_PAGES`), дальше кнопка меняет надпись на «Keep loading»; клик по ней обнуляет счётчик, и прокрутка снова работает. Ничего не обрезано — только сделано намеренным.

Число загруженных строк объявляется в `aria-live`: строки появляются без запроса, и для скринридера это единственный признак, что страница выросла.

### 15.3. Гонка ответов

У `load()` есть счётчик-талон, и ответ, не держащий последний, отбрасывается.

Без него хватало одного сценария: страница уже летит по прокрутке, посетитель жмёт чип. Ответ возвращается **после** первой страницы отфильтрованного списка и, будучи «догрузкой», дописывает свои строки к нему — 25 подходящих под фильтр серверов, а следом 16 не подходящих. Ловится это только руками и выглядит как случайное число строк.

### 15.4. Фильтры

| Параметр | Что делает |
| --- | --- |
| `status` | `online` · `players` · `full` · `empty` · `offline` |
| `map` | точное совпадение с тем, что сервер сам сообщил |
| `q` | подстрока в имени или хосте |
| `mode`, `version`, `country` | то же, что у фасетных маршрутов |
| `sort` | `rank` (умолчание страницы) · `players` · `newest` и остальные из `ServerListing::SORTS` |

**`empty` и `full` спрашиваются только у online-серверов.** Выключенный сервер по определению не держит игроков, и без этого условия он затопил бы корзину «пустые» машинами, к которым всё равно не подключиться. `full` дополнительно требует `players_max > 0`: сервер, ответивший без числа слотов, иначе удовлетворял бы `players_online >= players_max` при нуле и читался бы как забитый.

**`q` складывается в нижний регистр с обеих сторон** (`lower(name) like ?`). У Postgres `LIKE` регистрозависимый, у sqlite — нет, поэтому поиск «atlas» проходил мимо всех серверов, которые пишутся Atlas, и тесты этого не видели.

**Карты не слугифицируются.** `map` — свободный текст («Procedural Map», «discord.gg/atlasrust», «ВАЙП БЫЛ 6Ч НАЗАД»), у него нет канонической формы. Поэтому в фасете `slug` и `name` — это одно и то же значение, и оно же уходит в фильтр.

### 15.5. Счётчики на чипах

`facets.statuses` считается **по всей игре**, а не через уже применённые фильтры. Число, которое уменьшается по мере сужения, отвечает на вопрос «сколько осталось», а чипы стоят там, чтобы сказать, как игра выглядит целиком. Один агрегат вместо пяти запросов, и записан он через `sum(case when …)`, а не `FILTER`, чтобы тот же SQL работал под sqlite в тестах.

Чип с нулём показывается, но не нажимается: «на этой игре нет ни одного забитого сервера» — тоже ответ.

### 15.6. Сортировка по умолчанию

Страница просит `sort=rank` — это наш рейтинг, ради него всё и делается. Но `rank_score` равен нулю у сервера, за который никто не голосовал и который мы наблюдаем меньше недели, то есть у всего свежего каталога. Поэтому у `rank` есть добивка по `players_online`: иначе ранжированный список молодого каталога был бы упорядочен по порядку вставки, то есть никак.

### 15.7. Правый столбец

`GET /api/games/{game}/votes` — последние голоса по серверам игры. Единственный публичный след голоса, и намеренно тонкий: ник, который голосовавший сам опубликовал (чтобы владелец мог выдать награду), и время. `ip_hash` держит правило «один раз в сутки» и наружу не выходит; голос без ника остаётся анонимным и здесь.

Столбец появляется сбоку только с `2xl` — на 1280px он стоил бы таблице двух колонок; ниже он просто уезжает под список, а не прячется.

### 15.8. Флаги стран

Лежат в `web/public/flags/{код}.svg` — отдаёт Next, с того же origin, что и страница.

Не в `public/images/` на стороне Laravel, где лежит обложка игры: та — данные каталога, её скачивает `FetchGameArtwork`, путь хранится в `games.cover_path`, и каталог артворка поэтому в `.gitignore`. Флаг — не данные: набор фиксированный, API про него ничего не знает и знать не должен, файлы коммитятся.

**Набор — `country-flag-icons` (3x2), а не `flag-icons` (4x3).** Флаги те же, но 4x3 рисует каждый герб в полной детализации: Сербия 179 КБ, Мексика 85 КБ, Испания 79 КБ. SVGO снимает с них 1% — вес *и есть* графика. На 20 пикселях, где эти иконки живут, от герба не остаётся ни одной различимой линии. В 3x2 те же флаги весят меньше килобайта: 178 КБ на все 265.

Имена приводятся к нижнему регистру при копировании: API отдаёт ISO-код заглавными, компонент опускает его, и на регистрозависимой файловой системе (то есть в проде, а не на макбуке) `ES.svg` был бы 404 для каждого испанского сервера.

Пересобрать набор: `npm run flags:sync` (`web/scripts/sync-flags.mjs`). Пакет — devDependency, ни сборка, ни рантайм его не читают.

**Рядом с флагом всегда стоит код.** Половина флагов мира — три полосы, и на 16 пикселях несколько пар неразличимы; код же работает и запасным вариантом — страны приходят из GeoLite2, который знает их больше, чем есть в любом наборе иконок, и `onError` прячет картинку, оставляя подпись.

### 15.9. Лимит чтения

`RateLimiter::for('api')` поднят со 120 до 600 в минуту. Просмотр страницы — это не один запрос: оболочка тянет игру, выдачу и голоса, а живой слой потом перечитывает онлайн, пока вкладка открыта. Сборка фронта тяжелее ещё на порядок — она пререндерит все игры и читает этот же API с одного адреса так быстро, как может, и на 120 просто падала с 429. Записи, которые действительно стоит нормировать — голоса, заявки, коды входа, — лимитируются отдельно и не тронуты.

## 16. Блок Server information

Таблица фактов на странице сервера. Строка не рисуется, если значения нет — игра, которая не рассказывает про сиды и сущности, показывает меньше строк, а не столбец прочерков.

### 16.1. Что откуда берётся

| Строка | Источник |
| --- | --- |
| Players online, In queue | живой слой (`useLive`), не кешированная оболочка |
| Bots, Valve Anti-Cheat | A2S_INFO, колонки `bots` и `vac_enabled` |
| Location | GeoLite2 → `country_id` / `city` |
| Server language | вывод из текста, см. 16.3 |
| Map, Size, Seed, Mode, Build, PvE, FPS, Entities, Running for | A2S_RULES через `ServerInfo` |
| Version | `game_versions` или то, что сервер сообщил |
| Steam Server ID | EDF-блок A2S_INFO |
| Last wipe | тег `born` из keywords |
| Ping, Uptime | наши собственные замеры |
| Last update / online / offline, Added | `last_queried_at`, `last_online_at`, `last_offline_at`, `created_at` |

### 16.2. Боты, VAC и «последний раз офлайн»

`bots` и `vac_enabled` **всегда лежали в пакете** — драйвер читал оба байта и выбрасывал, потому что мимо них надо пройти, чтобы добраться до полей дальше. Теперь они сохраняются. Nullable, потому что у остальных протоколов такого понятия нет: у Minecraft-сервера нет ни ботов, ни VAC, и «мы не можем знать» — это не то же самое, что «ноль» и «выключено».

`last_offline_at` пишется при **каждом** неудачном опросе, а не только при первом в серии: строка отвечает на вопрос «когда он последний раз лежал», и во время аварии правильный ответ — «сейчас». В паре с `last_online_at` это и есть читаемая надёжность: «онлайн час назад, офлайн два дня назад» описывает сервер, который с тех пор стоит ровно.

### 16.3. Кнопка обновления

`POST /api/servers/{server}/refresh` — опрос по требованию, из угла заголовка блока.

Опрос идёт **прямо в запросе**, а не через очередь: на другом конце человек, который смотрит на панель и ждёт, когда она изменится, и выдать ему id задачи для поллинга — это худшая версия того же ожидания. Один опрос — это сокет и пятисекундный таймаут. Ответ — обычный `ServerDetailResource`, то есть новое содержимое панели целиком, плюс флаг `refreshed`.

**Две защиты, и они делают разное.** Лимитер на маршруте (6/мин на адрес) не даёт одному клиенту пройтись по каталогу. Кулдаун в контроллере — **на сервер**, поэтому никакое количество клиентов не заставит нас стучаться по одному адресу чаще: 60 секунд, половина самого горячего уровня каденции, то есть в худшем случае сервер, на который кто-то смотрит, проверяется вдвое чаще нашего собственного расписания. Это та защита, которая важна, потому что адрес чужой.

Внутри кулдауна запрос всё равно отвечает — текущим снимком и `refreshed: false`. Панель обновляется в любом случае, а «мы проверяли сорок секунд назад» — лучший ответ, чем ошибка. Фронт различает эти два случая тостом: без этого отказ по кулдауну выглядел бы ровно как опрос, ничего не нашедший.

**Свежий замер уходит в общий живой слой** (`useLivePublish`), а не остаётся в панели. Карточка подключения выше показывает тот же онлайн, и два разных числа на одном экране хуже, чем одно устаревшее.

### 16.4. Почему строка может не появиться сразу

Две разные причины, и их стоит различать.

**Замера ещё нет.** Поле, добавленное в мониторинг, заполняется у каждого сервера при его следующем опросе, а не у всех разом. Пока `bots` равен null, строки нет — это правильное поведение, «мы не знаем» не то же самое, что «ноль». Каталог доезжает за один цикл каденции: минуты для живых серверов, до шести часов для мёртвых.

**Оболочка страницы устарела.** Живой слой обновляет только счётчик игроков; карта, FPS, сущности, боты, античит, версия и время вайпа едут в закешированной выдаче страницы и до истечения окна не меняются. Оно стояло на `hours` — то есть сервер мог быть опрошен десяток раз, пока страница показывала, каким он был утром. Для сайта мониторинга это ровно то, чего делать нельзя; окно снижено до `minutes`.

Правильный ответ — чтобы Laravel дёргал `revalidateTag` при записи опроса: теги в `data.ts` заведены именно под это и **не вызываются ниоткуда**. Пока этого нет, гарантией остаётся длина окна, поэтому она должна быть короткой. См. открытые вопросы.

По той же причине на `minutes` переведены страницы списков и `getServers`: живой слой обновляет счётчики игроков, но **состав** списка — часть разметки, а владелец, только что добавивший сервер, идёт искать его именно туда.

### 16.5. Язык сервера

Его не сообщает никто. Ни A2S, ни Steam Web API, ни правила, которые публикует Rust — все ключи, что встречались в каталоге, перечислены в `ServerInfo`, и языка среди них нет. Поэтому он выводится из единственной улики: того, что владелец написал в имени и описании.

Два сигнала, по убыванию надёжности:

1. **Письменность.** Имя кириллицей — русскоязычный сервер, и контекст этого не меняет. То же для хангыля, каны, тайского, греческого, иврита и арабского. Ханьцзы намеренно нет: одни и те же иероглифы несут и китайский, и японский, а японский ловится по кане.
2. **Тег, который написал владелец.** `[RU]`, `(DE)`, `|BR|` в самом начале имени — осознанный сигнал игрокам, к которому все списки серверов приучили владельцев. Только в начале: в середине `[PVP]` и клан-теги неотличимы от заявки на язык.

Всё остальное возвращает null, и строки просто нет. Это и есть смысл конструкции: латинское имя не доказывает ничего — половина таких серверов английские, остальные польские, турецкие и португальские без тега, — а «English по умолчанию» превратило бы поле из факта в украшение. Страна по той же причине не используется: русскоязычные серверы каталога стоят в основном в Германии и Финляндии, потому что дешёвые машины там.

Ядро — `detect()` над обычными строками, без модели и без базы: будущий фасет «язык» должен будет прогнать это по всему каталогу и не захочет ни того, ни другого.

## 17. Сброс кеша фронта

Страницы каталога кешируются на минуты. Для чисел, которые дрейфуют сами, это верное окно; для изменения, которое человек только что сделал и вернулся посмотреть, — нет. Поэтому у окна есть напарник: событие.

```
POST /api/games/{game}/servers          (Laravel)
  ├─ сервер опрошен, записан, опубликован
  ├─ CatalogCounters::refresh()          денормализованные счётчики + сброс кеша API
  └─ FrontendCache::invalidate(...)  ──► POST /api/revalidate  (Next)
                                            revalidateTag(tag, { expire: 0 })
```

**Теги.** `games` — список игр и число рядом с каждой в меню. `game:{slug}` — выдача игры и её фасетные страницы. `servers` — любая выдача. `server:{slug}` — страница сервера. Проставлены и в `data.ts`, и **на самих страницах**: отрисованная страница — отдельная запись кеша, и распространение тегов внутрь-наружу документация не обещает.

**`{ expire: 0 }`, а не рекомендованное `"max"`.** `"max"` — это stale-while-revalidate: следующий посетитель получает старую страницу, а пересборка идёт за его спиной. Здесь это неверно, потому что этот посетитель — тот самый человек, который только что добавил сервер и вернулся его искать; ему показали бы список без него, ровно как до всей этой машинерии. Документация называет этот случай прямо: внешняя система дёргает Route Handler и требует немедленного устаревания. Платим тем, что первый пришедший ждёт отрисовку; добавления редки и лимитированы.

**Настройка.** `FRONTEND_REVALIDATE_URL` и `FRONTEND_REVALIDATE_SECRET` на стороне Laravel, `REVALIDATE_SECRET` — на стороне Next; секрет должен совпадать. Без любого из них ревалидация пропускается молча, и свежесть падает обратно на окно `cacheLife` — то есть туда, где была. Эндпоинт без секрета отвечает 503, с чужим — 401: адрес, по которому кто угодно может заставить сайт пересобирать все свои страницы подряд, это не эндпоинт, а мишень.

**Best effort.** Фронт может лежать, катиться или быть не настроен — ни одно из этого не повод завалить успешно принятую заявку. Ошибка пишется в лог и не всплывает наверх.

## 18. Открытые вопросы

1. **`wiped_at` — приближение.** Тег `born` строго означает «когда сервер последний раз стартовал». Для Rust это почти всегда вайп, но обычный рестарт тоже сдвигает значение. Если для сортировки «свежий вайп» этого окажется мало, придётся сверять с историей: настоящий вайп обнуляет онлайн и меняет карту, и это видно в `server_stats`.
2. **Отсечение по `max_per_host`** снижает каденцию серверам крупных хостеров. Сейчас это осознанный выбор в пользу вежливости; при росте каталога понадобится более умное распределение, чем «10 на батч».
3. **TTL челленджа проверен только до 30 секунд.** Стоит час; если серверы начнут отвечать `A` слишком часто, значение надо снизить — но заметить это можно только по метрикам, счётчика лишних обменов сейчас нет.
4. **Ревалидация вызывается только из формы добавления.** Механизм есть (раздел 17), но опрос сервера её не дёргает: это тысячи вызовов в минуту. Из-за этого измеренные поля на странице сервера по-прежнему живут в окне `cacheLife('minutes')`. Разумный следующий шаг — звать её из `QueryServer`, но только когда изменилось что-то, кроме числа игроков: карта, версия, вайп, статус.
5. **Счётчик в шапке игры и итог выдачи расходятся.** `games.servers_count` считает все активные серверы, а в списке видно только `verified()` — те, которых мы хоть раз успешно опросили. Разница — это кандидаты, добавленные формой или discovery и ещё ни разу не ответившие; на глаз это выглядит как «52 сервера» над таблицей из 51. Сходится само, как только сервер отвечает, но если расхождение станет заметным, счётчик надо считать по той же выборке, что и список.
